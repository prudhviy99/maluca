# Maluca Triage — AI Incident Triage Agent

**Spec + implementation plan** · v0.1 · 2026-08-07

An LLM-powered agent that watches Maluca's mitigation decisions, detects
traffic-anomaly incidents, explains them with runbook-cited root-cause
analysis, and proposes (never silently applies) policy changes — all on
local inference.

Resume claim this project backs:

> AI Incident Triage Agent | Java, Spring AI, PostgreSQL/pgvector, Ollama
> — pgvector-backed runbook retrieval with source-cited remediation, MCP
> operational tools, local Ollama inference, and prompt/output regression
> evaluation.

---

## 1. Goals & non-goals

### Goals

1. **Detect** incident windows from Maluca's decision stream (e.g. BLOCK
   rate spikes on a route) without human prompting.
2. **Triage**: classify the incident (burst flood / path scan / credential
   stuffing / low-and-slow / Redis degradation / false-positive wave) with
   a grounded explanation citing actual decision data — client keys, the
   dominant `contributions` entries, affected routes.
3. **Retrieve** the matching runbook chunks from pgvector and cite them by
   source + heading. Responses with citations outside the retrieved set
   are rejected and retried.
4. **Propose** a concrete remediation as a policy diff against
   `config/policies.yml` semantics (`PolicyDefinition`), gated behind human
   approval; apply via `POST /_maluca/admin/policies/reload` only after
   approval.
5. **Expose** the same operational capabilities as an MCP server usable
   from any MCP client (Claude Code, etc.).
6. **Evaluate**: a regression suite with frozen incident fixtures
   (generated by `scripts/traffic/*.py`) asserting classification,
   citation, and proposed-action correctness in CI.

### Non-goals

- **No LLM in the request path.** `maluca-proxy`'s ~5ms p99 added latency
  is untouched. Triage is a separate process on a separate stack.
- No auto-remediation without approval (dry-run/propose only by default).
- No cloud LLM dependency — Ollama is the only inference backend. (The
  Spring AI `ChatModel` abstraction keeps a swap possible, but it is not a
  supported configuration.)
- No general log analytics; the agent reasons over Maluca decisions and
  Prometheus metrics only.
- Not a chatbot UI. Interface is: triage reports (API + Markdown), the MCP
  server, and CI eval output.

## 2. Architecture

```
                 ┌────────────────────────────────────────────┐
   client ─────▶ │ maluca-proxy (WebFlux, hot path)           │ ─────▶ backend
                 │  + DecisionSink (async, bounded, lossy-ok) │
                 └──────────────┬─────────────────────────────┘
                                │ batched INSERTs           /actuator/prometheus
                                ▼                                    │
                 ┌────────────────────────────┐                      │
                 │ PostgreSQL 16 + pgvector   │                      │
                 │  decisions   (events)      │                      │
                 │  incidents   (windows)     │                      │
                 │  runbook_chunks (embedded) │                      │
                 │  triage_reports            │                      │
                 └──────────────┬─────────────┘                      │
                                │                                    │
                 ┌──────────────▼─────────────────────────────────── ▼ ──┐
                 │ maluca-triage (Spring Boot, servlet, virtual threads) │
                 │                                                       │
                 │  AnomalyDetector ──▶ TriageAgent (Spring AI)          │
                 │                        │  RAG: pgvector retrieval     │
                 │                        │  tools: MCP client ──┐       │
                 │                        ▼                      │       │
                 │                  TriageReport (structured,    │       │
                 │                  citation-validated)          │       │
                 │  MCP server (same tools, exposed outward)◀────┘       │
                 └───────────────┬───────────────────────────────────────┘
                                 │ chat + embeddings
                                 ▼
                          Ollama (GPU, RTX 5080)
                            qwen3:14b + nomic-embed-text
```

**Module layout** (new Gradle subprojects; `maluca-proxy` gets one small
addition):

```
maluca-triage/         agent, anomaly detector, RAG, report API, evals
maluca-mcp/            MCP server exposing operational tools
maluca-proxy/          + state/DecisionSink.java (only change)
docs/runbooks/         one runbook per incident class (RAG corpus)
```

`maluca-mcp` could live inside `maluca-triage`; it is split so the MCP
server can run against a live proxy without the agent (useful for the
Claude Code demo and for keeping tool code honest — the agent consumes
tools only through MCP, same as any external client).

### Key decisions

| Decision | Choice | Why |
|---|---|---|
| How the agent sees decisions | Proxy writes to Postgres via async sink | Decision logs are stdout-only today; a queryable store is the enabler for everything else. Postgres is already being added for pgvector. |
| Sink failure mode | Bounded queue, drop-oldest, counter metric | The proxy must never block or error because triage storage is slow/down. Losing decision rows under pressure is acceptable; losing requests is not. |
| Triage stack | Spring MVC + virtual threads (not WebFlux) | Agent work is coarse-grained and latency-insensitive; blocking style keeps Spring AI + JDBC code simple. Deliberate contrast with the proxy is a good talking point. |
| Agent ↔ tools | Agent is an MCP *client* of `maluca-mcp` | One tool implementation serves both the agent and external MCP clients; forces clean tool contracts. |
| Write actions | `propose_policy_patch` returns a diff; separate approval step applies | Mirrors Maluca's own `DRY_RUN`/`ENFORCE` vocabulary. LLM output is never directly executed. |
| Embeddings | `nomic-embed-text` via Ollama, 768-dim | Local, fast, well-supported; corpus is tiny (~6 runbooks) so quality ceiling is set by chunking, not model size. |
| Chat model | `qwen3:14b` q4 default; `llama3.1:8b` fallback | Fits 16GB VRAM with context headroom; decent tool calling. Model name is config, not code. |

## 3. Component specs

### 3.1 DecisionSink (change to `maluca-proxy`)

The only proxy modification.

- New `DecisionSink` component alongside `DecisionLogger`; the
  `MitigationWebFilter` call site invokes both.
- API: `void offer(DecisionEvent e)` — non-blocking enqueue into a bounded
  in-memory queue (default 10 000; drop-oldest on overflow, increment
  `maluca_sink_dropped_total`).
- A single virtual-thread (or scheduled) drainer batches up to 500 events
  / 1s flush interval into `INSERT ... ON CONFLICT DO NOTHING` via R2DBC
  or plain JDBC on a dedicated thread — either is fine because it is off
  the event loop entirely.
- Config-gated: `maluca.sink.enabled=false` by default so the proxy
  remains standalone; the compose file for triage turns it on.
- `DecisionEvent` fields: `ts`, `client_key`, `action`, `score`, `path`,
  `route`/`policy`, `reason`, `contributions` (jsonb), `dry_run`, `tier`.

**Acceptance:** latency bench (`scripts/bench/latency_bench.py`) shows no
measurable p99 regression with sink enabled and Postgres *stopped*.

### 3.2 Schema (Postgres 16 + pgvector, Flyway-managed in `maluca-triage`)

```sql
decisions(id bigserial, ts timestamptz, client_key text, action text,
          score int, path text, policy text, reason text,
          contributions jsonb, dry_run bool, tier text);
-- BRIN index on ts; btree on (policy, ts), (action, ts)

incidents(id, opened_at, closed_at, route text, trigger text,
          status text,            -- OPEN | TRIAGING | TRIAGE_FAILED | TRIAGED | ...
          stats jsonb,            -- window aggregates snapshotted at detection
          triage_lease_id uuid, triage_claimed_at timestamptz,
          triage_attempts int, triage_next_attempt_at timestamptz);

triage_reports(id, incident_id, created_at, model text,
               classification text,      -- enum, see §3.4
               confidence text,          -- LOW | MEDIUM | HIGH
               summary text, evidence jsonb,
               citations jsonb,          -- [{source, heading, chunk_id}]
               proposed_patch jsonb,     -- policy diff or null
               raw_response text);       -- for eval/debug

runbook_chunks(id, source text, heading text, content text,
               embedding vector(768), updated_at);

decision rows are pruned by a scheduled job (default retention 7 days).
```

### 3.3 AnomalyDetector

Deterministic, no LLM. Polls `decisions` every 15s (configurable):

- **Rule A — mitigation spike:** non-ALLOW share of decisions for a
  (route, 60s window) exceeds N× its trailing 15-min baseline and an
  absolute floor (e.g. ≥ 30 mitigated requests).
- **Rule B — challenge/block surge:** CHALLENGE+BLOCK count ≥ threshold.
- **Rule C — redis degradation:** `maluca_redis_errors_total` delta > 0
  via Prometheus query (this incident class never shows in decisions
  as such).
- Debounce: one OPEN incident per route at a time; auto-close when the
  window normalizes for 5 min.

Opening an incident snapshots window aggregates into `incidents.stats`
(top client keys, action histogram, top paths, mean/max score, top-3
aggregate `contributions` signals) — the LLM receives *this compact
summary plus sampled raw rows*, not thousands of events.

### 3.4 TriageAgent

Spring AI `ChatClient` against Ollama. Flow per incident:

1. Build the **incident brief** from `incidents.stats` + ≤ 50 sampled
   decision rows (stratified by action).
2. **Retrieve**: embed the brief, top-k (k=6) cosine search over
   `runbook_chunks`; include chunks above similarity floor.
3. **Prompt** = system prompt (role, output contract, "cite only provided
   chunks") + brief + chunks (each tagged `[chunk_id source#heading]`) +
   tool access (read-only MCP tools, for follow-up queries the brief
   doesn't answer).
4. **Structured output** into a Java record:

   ```java
   record TriageResult(
       Classification classification,   // BURST_FLOOD, PATH_SCAN,
                                        // CREDENTIAL_STUFFING, LOW_AND_SLOW,
                                        // REDIS_DEGRADATION,
                                        // FALSE_POSITIVE_WAVE, UNKNOWN
       Confidence confidence,
       String summary,                  // ≤ 150 words, must reference concrete
                                        // evidence (client keys, signals)
       List<Citation> citations,        // chunk_ids
       PolicyPatch proposedPatch)       // nullable
   ```

5. **Validation gate** (code, not model): parse OK; every `chunk_id` ∈
   retrieved set; patch (if present) deserializes as a valid
   `PolicyDefinition` delta and touches only the incident's route. On
   failure → one retry with the validation error appended; second failure
   → store a diagnostic report with `classification=UNKNOWN,
   confidence=LOW` and the raw response for postmortem, then apply the
   bounded incident retry/backoff budget instead of declaring triage
   complete. Never discard silently.
6. Persist `triage_reports`; render a Markdown report; expose via API.

`UNKNOWN` is a first-class honest answer, not an error state.

### 3.5 MCP server (`maluca-mcp`)

Spring AI MCP server (streamable-HTTP). Flat schemas, few tools:

| Tool | Access | Contract |
|---|---|---|
| `get_incidents(status?, limit?)` | read | Recent incidents + stats |
| `get_decisions(route?, client_key?, action?, from, to, limit≤200)` | read | Sampled decision rows |
| `get_signal_breakdown(route, from, to)` | read | Aggregated `contributions` by signal |
| `query_metrics(promql, from?, to?)` | read | Proxied to Prometheus HTTP API, response truncated |
| `list_policies()` | read | Proxied from `GET /_maluca/admin/policies` |
| `search_runbooks(query, k?)` | read | pgvector search, returns chunks with ids |
| `propose_policy_patch(incident_id, patch)` | write-propose | Validates patch, stores on report, status → TRIAGED. **Never applies.** |
| `approve_and_apply(incident_id, proposal_id, expected_proposal_sha256, expected_policy_sha256, expected_incident_version)` | write-apply | Human-only path on the separate `/operator/mcp` server: binds approval to the exact reviewed proposal, rewrites `policies.yml`, calls `/reload`, and verifies the active projection. It is absent from `/mcp` and disabled by default. |

The TriageAgent connects as a client with the read + propose set only.

### 3.6 Runbook corpus (`docs/runbooks/`)

Seven documents, one per concrete incident class (§3.4 enum minus UNKNOWN). Uniform
structure so heading-based chunking works: **Symptoms** (which signals
dominate `contributions`, expected action mix) / **Confirm** (queries to
run) / **Remediate** (which `PolicyDefinition` knobs: bands, rate-limit
algorithm/limits, mode, deny/allowlist) / **False-positive checks** /
**Rollback**. Chunk = one H2 section; metadata = `{source, heading}`.
An `IngestRunner` (CLI/startup task) re-embeds on content hash change.

### 3.7 Eval harness (the regression-evaluation claim)

Two layers, both JUnit in `maluca-triage/src/test`:

**Layer 1 — deterministic (CI, no GPU, no LLM):**
- Retrieval evals: for each frozen incident brief, assert the expected
  runbook is in top-k. Embeddings for fixtures are pre-computed and
  committed, so CI needs no Ollama.
- Validation-gate evals: recorded good/bad model outputs (bad citations,
  malformed patches, wrong-route patches) → gate accepts/rejects
  correctly.
- AnomalyDetector evals: synthetic decision-row sets → expected
  incidents opened/not opened.

**Layer 2 — model-in-the-loop (nightly / local, tagged `@Tag("llm")`):**
- **Fixtures**: run each `scripts/traffic/*.py` scenario against the live
  stack once; freeze the resulting incident brief + sampled rows as JSON
  under `src/test/resources/fixtures/`. Ground truth is the script that
  generated it.
- Assert per fixture: `classification` matches label; ≥1 citation from
  the matching runbook; patch class is sane (e.g. cred-stuff ⇒ tightens
  the `/login` route, not global); `normal.py` fixture ⇒ no incident, or
  `FALSE_POSITIVE_WAVE`/low-confidence if forced.
- Score = pass-rate across fixtures × N repetitions (temperature 0);
  regression = drop vs the committed baseline in `evals/baseline.json`.
  Prompt changes require re-running and committing the new baseline —
  that diff *is* the prompt-regression story.
- Prose quality (summary references concrete evidence, no invented
  numbers) checked by a rubric prompt against the same local model —
  advisory, non-blocking.

### 3.8 Infra

Extend `docker-compose.yml` with a `triage` profile:

- `postgres`: `pgvector/pgvector:pg16`, volume, healthcheck.
- `ollama`: official image with NVIDIA runtime
  (`deploy.resources.reservations.devices` gpu), volume for models,
  `ollama pull` init for `qwen3:14b` + `nomic-embed-text`.
- `maluca-triage`: depends_on postgres+ollama healthy; env-configured
  model names, thresholds, Prometheus URL.
- `maluca-proxy` gains `MALUCA_SINK_ENABLED=true` + datasource env in
  this profile only.

GPU note: RTX 5080 (Blackwell/sm_120) requires a recent Ollama with CUDA
12.8+. Verify `ollama ps` reports 100% GPU before benchmarking anything.

## 4. Implementation plan

Each phase ends green (`./gradlew check`) and demoable. Mirrors Maluca's
own phased history.

### Phase 1 — Decision sink + schema
- `maluca-triage` module skeleton, Flyway migrations (§3.2), compose
  `triage` profile with Postgres.
- `DecisionSink` in the proxy (config-gated), drop-oldest queue,
  batch insert, `maluca_sink_dropped_total`.
- Tests: Testcontainers Postgres; sink survives DB-down (drops, counts,
  proxy unaffected); latency bench comparison documented.
- **Demo:** run `burst.py`, `SELECT` the decisions with contributions.

### Phase 2 — Anomaly detection
- `AnomalyDetector` rules A–C, incident lifecycle, stats snapshot,
  debounce/auto-close. Prometheus HTTP client for rule C.
- Tests: synthetic-row unit tests (these become Layer-1 evals).
- **Demo:** `burst.py` → incident row opens with correct stats; `normal.py`
  → nothing.

### Phase 3 — Ollama + naive agent (no RAG)
- Ollama container + Spring AI wiring; `TriageAgent` v0: brief → prompt →
  `TriageResult` structured output → validation gate (parse-only) →
  stored report; Markdown rendering; `GET /triage/incidents/{id}/report`.
- **Demo:** end-to-end burst → readable triage report from local GPU.

### Phase 4 — Runbooks + RAG + citation enforcement
- Write the seven runbooks; chunking + `IngestRunner` + pgvector search.
- Citation validation in the gate; retry-then-UNKNOWN path.
- Tests: retrieval evals with committed fixture embeddings; gate evals.
- **Demo:** report now cites `runbook#heading`; a doctored bad citation
  gets rejected and retried.

### Phase 5 — MCP server + agent-as-client
- `maluca-mcp` module: read tools + `propose_policy_patch` (§3.5).
- Point the agent's tool access at it; delete any direct-DB tool code
  from the agent.
- **Demo:** add the server to Claude Code (`claude mcp add`) and triage an
  incident interactively; the in-process agent uses identical tools.

### Phase 6 — Eval harness + baseline
- Generate and freeze the seven incident fixtures; Layer-1 suite in CI
  (GitHub Actions, no GPU); Layer-2 `@Tag("llm")` runner + scoring +
  `evals/baseline.json`; document the re-baseline workflow.
- **Demo:** intentionally degrade the system prompt → eval run fails
  against baseline.

### Phase 7 — Approval + apply loop, packaging, docs
- `approve_and_apply`: patch → `policies.yml` rewrite → admin `/reload`
  → verify via `list_policies` → status APPLIED; rollback notes on the
  incident.
- `maluca-triage/README.md` (own story, per repo convention), runbook on
  the triage service itself, top-level README link, Grafana panel for
  incidents/sink metrics.
- **Demo (the headline):** `credstuff.py` → incident → cited report
  proposing tighter `/login` bands → approve → policy hot-reloads →
  rerun `credstuff.py` → blocked earlier. Full loop, no cloud.

### Sizing

Phases 1–3 are the plumbing hump (~half the effort); 4–6 are where the
resume claims are earned; 7 is the payoff demo. Phases 1–2 are useful
even if the project stops there (queryable decision history + anomaly
alerts with zero LLM involvement).

## 5. Risks

| Risk | Mitigation |
|---|---|
| 14B model tool-calling flakiness | Few flat tools; brief contains most context up-front so tool use is optional; validation gate + retry; `UNKNOWN` fallback. |
| Eval flakiness blocking CI | Layer 1 (deterministic) gates CI; Layer 2 is nightly/local with N-repetition pass rates. |
| Sink hurts the proxy's latency story | Config-gated, drop-oldest, off-event-loop; re-run bench in Phase 1 and publish the number. |
| Scope creep into a second mega-project | Phases are independently shippable; MCP server and detector have standalone value; stop-points after 2, 5, 6 are all coherent. |
| Ollama/Blackwell CUDA mismatch → silent CPU fallback | Startup check: log `ollama ps` GPU status; document required Ollama version. |
